# תוצאות: תיקון מסלול הכתיבה של ה-outbox (דגל `OUTBOX_SNAPSHOT_FAST`) — 8.11.2026

**סטטוס:** מימוש + בדיקות מקומיות הושלמו. **לא נפרס.** הדגל כבוי כברירת מחדל. ממתין לסקירה חוזרת של קודקס. תוכנית ואישור קודקס: `docs/outbox-write-path-fix-plan-for-codex-2026-11-08.md` (§10).

## מה שונה (src/database.ts)
- `cloneSnapshotForTablesPlanned` (ועטיפה `cloneSnapshotForTables` ללא שינוי חתימה): כשהדגל דולק וה-outbox מסומן ברמת שורות — אינדקס `id→מיקום` מצטבר ב-`WeakMap` לפי המערך החי; `next = previous.slice()`, ורק השורות המסומנות משוכפלות ומוצבות במיקומן החי. כל אי-עקביות (מזהה לא נמצא, שורה חדשה שלא סומנה, אי-יישור מול העותק הקודם, דגימה אקראית של מזהים, כפילות מזהה) ← `null` וחזרה למעבר המלא המקורי.
- בדיקת צל כל `OUTBOX_SNAPSHOT_SHADOW_EVERY` (ברירת מחדל 50) אצוות, **לפני** הכתיבה: השוואה לעותק המלא; באי-התאמה — כותבים את המלא, `[SNAPSHOT_FAST_MISMATCH]`, והמסלול המהיר כבה בתהליך.
- `writeSnapshotDelta` / `syncOutboxMessagesDelta` / `syncRowsDeltaTracked` מקבלים `positions` כפרמטר מפורש (לא Symbol); אימות יישור **לפני הכתיבה הראשונה**, ובכל ספק — המסלול הישן.
- ללא הפרמטר או עם הדגל כבוי: התנהגות זהה לקודמת.

## בדיקות
- חדש: `scripts/test-snapshot-fast-path.js` (`npm run test:snapshot-fast-path`, ברשימת הרגרסיה): 25 seeds אקראיים (הוספה/עדכון/אצווה שנכשלה בסביבת commit), סדר סימון שונה מסדר הוספה, שורה חדשה לא מסומנת, שינוי סדר פנימי, החלפה באותו אורך, מחיקה, כשל COMMIT + restart + retry, דגל כבוי. מושווים snapshot וטבלת ה-DB (מדומה) לנתונים החיים בכל צעד. עובר (5 ריצות רצופות).
- הקיימות (outbox / postgres-dirty-tables / row-snapshot / attempts / uncertain / delta / no-lost-writes / transactions / burst / evidence / delivery-recovery): עוברות, גם עם `OUTBOX_SNAPSHOT_FAST=1` + צל על כל אצווה, מול PostgreSQL מקומי.

הכפילויות (3) והסידור (1) בריצת הדגל: כולן בקמפיין B, אצל הלקוחה שנהרגה ב-`kill-client@260:B` (SIGKILL), שליחה חוזרת כ-65–68 שניות אחרי ניסיון ראשון "accepted". זה המנגנון המוכר של הריגה בין קבלת Meta לרישום `sent` (CLAUDE.md מגבלה 6; ריצות קודמות בלי השינוי הראו 47–48 כפילויות תחת תרחישים דומים). **ריצה אחת לכל צד אינה מבדילה בין רעש לתלות בתיקון** — לא הוכח שהתיקון לא תורם, ולא הוכח שכן.

1. להריץ catastrophe עוד פעם-פעמיים לכל צד (או להצמיד seed) כדי לראות אם הכפילויות תלויות בדגל.

3. ההאטה בייצור גדולה פי ~10 מהניסוי; אין הבטחה שהתיקון פותר את כולה — נדרשת מדידת lag/snapshot_ms בייצור אחרי הפריסה.
